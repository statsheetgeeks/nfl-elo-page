# NFL Elo — GitHub Pages site

A self-updating NFL Elo rankings site: three rating tables (Combined, Classic
Elo, G-Elo margin-of-victory), the current week's games with predictions and
starting QBs, and a running track record with a confidence-calibration
breakdown.

## How it runs

- **`.github/workflows/update.yml`** runs the pipeline every **Wednesday at
  5pm ET** (cron, UTC-adjusted), and also exposes a **manual trigger**: go to
  the repo's Actions tab → "Update NFL Elo ratings" → "Run workflow", or
  `gh workflow run update.yml` from the CLI. Both paths run the exact same
  script, so a manual run mid-week behaves identically to the scheduled one.
- **Week rollover**: the pipeline will not advance to the next week until
  *every* game in the current week — including Monday Night Football — has
  a final score (`pipeline/week_logic.py`). Running it manually on, say, a
  Thursday just refreshes the current week's ratings/predictions; it won't
  jump ahead until Monday night's game is complete.
- Each run **writes JSON into `docs/data/`** and commits it back to the repo.
  GitHub Pages serves `docs/` as the site, so a completed run is what makes
  the live page update — nothing else to deploy.

## One-time setup

1. Push this repo to GitHub.
2. Repo Settings → Pages → set source to "Deploy from a branch", branch
   `main`, folder `/docs`.
3. Repo Settings → Actions → General → Workflow permissions → set to
   "Read and write permissions" (needed so the workflow can commit
   `data/` and `docs/data/` back to the repo).
4. Run the workflow once manually to populate real data (see below) —
   the site ships with a small hand-written **sample** dataset in
   `docs/data/` just so the page isn't blank on first deploy; it gets
   overwritten by the first real pipeline run.

## Repo layout

```
pipeline/
  model.py              ClassicElo + GEloAC rating engines
  espn_client.py        ESPN public JSON endpoints: schedule/scores, starting QB, injuries
  week_logic.py          "has the week finished?" rollover rule
  build_site_data.py     orchestrator: sync history -> replay ratings -> grade
                          last week's predictions -> build this week's
                          predictions -> write docs/data/*.json
  starter_overrides.json manual QB overrides (see below)
  requirements.txt

data/
  games_history.csv      append-only record of completed games (built up over time)
  predictions_log.csv    every prediction, graded once its game finishes
  state.json             last-known current week (avoids re-scanning the season)

docs/                     the GitHub Pages site
  index.html, styles.css, app.js
  data/*.json             generated by the pipeline; the site fetches these at runtime
```

## Data sources and known rough edges

- **Scores/schedule**: ESPN's public (unofficial) scoreboard JSON. Reliable
  and free, but undocumented — if ESPN changes response shape, `parse_games`
  is the one place to fix it.
- **Starting QB**: pulled from ESPN's team depth-chart endpoint. This is the
  part most likely to need a look on the very first live run — the exact
  JSON path for "who's QB1" has shifted before. If a card shows "TBD" for a
  team that clearly has a known starter, check `espn_client.get_starting_qb`
  against a real response for that team.
- **Manual overrides**: `pipeline/starter_overrides.json` lets you hard-set
  a team's starter (e.g. `{"NYG": "Jameis Winston"}`) for cases where the
  live source is wrong or hasn't updated yet — exactly the Dart/Winston
  situation that prompted this feature. Remove the override once the live
  source catches up.

## Combined rating

`combined_ratings()` is currently a simple average of ClassicElo and GEloAC.
That's a placeholder worth revisiting once there's enough graded-prediction
history to justify a weighted blend (e.g. weight whichever engine is
currently better calibrated in `predictions_log.csv`).

## Testing locally without hitting ESPN

`pipeline/build_site_data.py`'s network calls (`sync_history`,
`get_starting_qb`, `determine_current_week`) need outbound internet, which
this dev environment didn't have. Everything else — rating replay,
Combined-rating blending, rank-change arrows, and prediction grading — was
verified locally by writing rows directly into `data/games_history.csv` and
a fake `docs/data/predictions.json`, then calling `replay_ratings()`,
`build_rankings()`, and `grade_completed_predictions()` directly. Worth
doing a similar dry run yourself (or just watching the first Actions run's
logs closely) to confirm the ESPN parsing holds up against live data.
